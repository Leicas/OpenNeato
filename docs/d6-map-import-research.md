# D6 native map import research

Research snapshot: 2026-11-14. Target observed on this installation: Botvac D6,
firmware `4.5.3-189` (Gen3). No script, map, or firmware was uploaded, and no
cleaning cycle or network/factory reset was started. The later debug phase
performed one controlled normal power cycle, described below.

## Conclusion and integration boundary

The server-side consensus can improve an operator's plan and planning decisions.
It is not yet a native navigation map that the D6 can load. A supported raster
import was not found in the examined Gen3 interfaces. That is a limit of the
current evidence, **not proof that native map restoration or replacement is
impossible**. The next useful experiment is to inventory the running QNX system
and export the native map artifacts and the code that reads them.

Keep analysis and map fusion in a server companion to Vacuula. Use OpenNeato for
serial telemetry and the existing bridge; use Home Assistant for scheduling and
presentation. The ESP32 does not need to run registration or consensus. The
candidate plan must remain distinct from the native reference and cannot become
an alignment reference recursively without independent validation.

## Three different map products

| Product | Established meaning | What it does not establish |
|---|---|---|
| `FloorMap.png` / derived `floormap.json` | Rendered SLAM floor grid; parser classifies unknown/free/wall | Complete localization state or an accepted import format |
| `RunMap.png` / derived `runmap.json` | Where the robot drove, plus dock markers | Suction/brush activity, room completion, or localization landmarks |
| Native persistent-map artifacts | Referenced by a map ID and loaded by the robot | Files, internal serialization, and dependencies have not yet been inventoried on this D6 |

The current Vacuula Gen3 parser labels floor cells `0=unknown`, `1=free`,
`2=wall`. Its path parser preserves values: `128` is background, `100/200` mark
the dock, other values identify passages. JSON RLE is generated by the server
from the received images. Modifying that JSON changes a presentation artifact;
there is no demonstrated reverse path from it to the D6's native SLAM state.
[Parser source](https://github.com/vacuula/vacuula/blob/1d20dd6650d02251c36146003cca168da12971fa/server/src/vacuula_server/gen3/map_utils.py)

## Interfaces confirmed in the examined code

The installed Gen3 web client sends `getMapBoundaries` and `setMapBoundaries`
with `mapId`, and supports `startPersistentMapExploration`. Zone cleaning sends
`startCleaning` with `category`, `mapId`, and `boundaryId`. These are boundaries
and native exploration operations, not arbitrary occupancy-grid import.
[Gen3 command client](https://github.com/vacuula/vacuula/blob/1d20dd6650d02251c36146003cca168da12971fa/app/src/http/gen3.ts)

On the server, Gen3's `/persistent_maps` supplies IDs of enabled persistent maps.
Its map-upload handshake receives `FloorMap.png`, `RunMap.png`, and
`manifest.json` **from the robot**. The application map-edit route updates name
and enabled state in the database. None of those handlers was an image restore
operation. The installed `/promote` route dispatches to Gen4 code, so its
`maps.promote_floorplan` behavior cannot be assumed to apply to the D6.
[Gen3 map handlers](https://github.com/vacuula/vacuula/blob/1d20dd6650d02251c36146003cca168da12971fa/server/src/vacuula_server/gen3/handlers/beehive.py),
[application handlers](https://github.com/vacuula/vacuula/blob/1d20dd6650d02251c36146003cca168da12971fa/server/src/vacuula_server/handlers/app.py)

Repository serial documentation lists persistent cleaning and authenticated
events, but no native map-file import. It also records that `Clean Stop` can
discard localization on D7 `4.6.0`; that observation must not be generalized to
this D6 firmware without validation. See
[serial protocol](neato-serial-protocol.md).

The older `Philip2809/neato-connected` link now redirects to
[vacuula/fang](https://github.com/vacuula/fang). Its public research material
documents diagnostic commands but did not supply a native D6 map format or a
restoration mechanism in this review. Historical Botvac Connected shell research
concerns an older generation and is not evidence that the same exploit or
filesystem layout applies to this D6.

## Direct evidence from the running D6

The existing OpenNeato serial bridge was used to request `Help` and then only
the help topics `CopyDumps`, `GetState`, `GetSysLog`, `Upload`, and
`SetSystemParameter`. Those underlying commands were not executed by these
probes. The local private transcripts are named `live-Help*.txt` in the firmware
investigation directory.

The general help response lists 44 command entries. It exposes cleaning,
diagnostics, settings, and program upload, but no named map import or map-file
restore. `Help Upload` describes program upload, not a map restore. Several
undocumented-command help topics give no usable description. The help table is
known to omit working authenticated events, so the empty topics and missing
map command are **not** evidence that no internal map loader exists.

This live probe strengthens the boundary between the available diagnostic API
and a still-unidentified native-map mechanism. It does not inspect the QNX
filesystem or prove the capabilities of the `Robot` process.

## The D6 runs QNX; distinguish cloud code from navigation code

The Gen3 installer uses QNX facilities (`pidin`, `slay`, `qdbc`, `/dev/qdb/*`)
and patches `/usr/bin/astro`. It supports this exact firmware build. It also
refers separately to `Robot`/`fileuploader` loading `libNeatoUploader.so.1`.
The installer patch concerns cloud certificates and connectivity; it does not
demonstrate a navigation-map decoder or serializer.
[Pinned installer source](https://github.com/vacuula/installer/blob/d8a1510e414217515de24cbca3494eaca8475bd9/src/assets/scripts/gen3/vacuula.sh)

The current upstream tools mechanism can execute an uploaded temporary shell
script through the copy-dumps hook. Its presence on this robot is **not
confirmed**: the older installer commit pinned by the local provisioning branch
does not contain `tools.sh`. `firmwareSupported` and `skeyReady` only describe
the bridge's serial capabilities. Do not probe the hook by calling `CopyDumps`:
the stock command copies dumps to EMMC. Prove the hook independently before
using it. No SSH server, Linux tools, or remote interactive shell is assumed.
[Tools script](https://github.com/vacuula/installer/blob/d8a1510e414217515de24cbca3494eaca8475bd9/src/assets/scripts/gen3/tools.sh)

The initialization script exposes QDB endpoints `/dev/qdb/systemdb` and
`/dev/qdb/robotdb`. Those are database service endpoints, not established ordinary
files to copy. Full settings output can contain credentials: inspect table names
first, then only relevant schemas/rows with redaction.
[Initialization source](https://github.com/vacuula/installer/blob/d8a1510e414217515de24cbca3494eaca8475bd9/src/assets/scripts/gen3/init.sh)

the running QNX filesystem is a more direct research path than reflashing the
encrypted update.

## Live debug boot and native metadata, 2026-11-14

The robot's own `Help SetSystemMode` distinguished `PowerCycle` from `Shutdown`
and `Standby`. Before the experiment, HA reported docked, battery 100%, external
voltage 18.63 V, and the bridge reported `ST_C_Standby`. The sequence was
`TestMode On`, `SetSystemMode PowerCycle`, a bounded UART capture, resume serial
polling, then `TestMode Off`. No boot-menu keystrokes or update were sent.

The command returned `Exited robot with RETCODE 304 ...`. Sixteen captured idle
lines included `Not factory boot...`, `Booting Main Image`, and the existing

standby; live cloud state confirmed docked, charging, no error and no alert.
This capture did not expose a QNX shell or establish arbitrary file access.

Vacuula reconnected after the normal reboot. The following reads were then
performed on the real D6:

|---|---|
| `getRobotState` | `ok`; standby, docked and charging, 100% battery |
| `getGeneralInfo` | `ok`; D6, product 905-0496, firmware 4.5.3-189 |

The last result is a rejected RPC name, not evidence that the robot went

## Next experiment: acquisition, then format proof

1. **Inventory without changing persistent state.** Confirm the running firmware
   and process names; list the bounded `/usr/bin`, `/usr/lib`, `/emmc`, and
   `/var/app_data` trees. Inspect QDB table names and map-related schemas only.
   Do not infer Gen3 paths from Gen4 `/user/databases/mapsdb` examples.
2. **Export selected native material.** Obtain the navigation executable
   (`/bin/robot` and case-sensitive `Robot` are candidates, exact path to verify), relevant loaded
   libraries, map-related configuration, native map files, IDs, and boundary
   metadata. Hash exports locally and keep private copies outside Git. Avoid
   copying Wi-Fi keys or unrelated robot secrets.
3. **Inspect offline.** Read ELF architecture/symbols and strings, trace native
   map-open/store/load functions and filenames, identify version fields,
   checksums, coordinate scale/origin, dock pose, localization features, and
   database relationships. Do not assume the map is only a bitmap; establish
   which of those components actually exists.
4. **Prove an unchanged round trip offline.** Parse and reserialize an exported
   native map byte-for-byte where possible. Identify every dependent artifact
   before attempting restore. Editing visible pixels is insufficient evidence.
5. **Separate restoration from fusion.** First establish restoration of an
   unmodified native snapshot with a complete backup and a verified rollback
   procedure. Only then evaluate a deliberately modified candidate on a spare
   reference/robot or a tightly controlled test. Neither experiment is part of
   the current read-only acquisition.
6. **Fallback that uses proven native behavior.** If import remains impractical,
   create a fresh native map through exploration, then preview and transform the
   existing zones into that map's coordinate frame. This improves future
   scheduling without claiming that the server rewrote the SLAM engine.

The practical question is therefore: **what native artifact set does `Robot`
load, and can that exact set be restored transactionally?** Once answered, a
conversion from a consensus grid can be evaluated rather than assumed.

## REA: capabilities and an actual trial on this firmware

The REA in question is [morluto/rea](https://github.com/morluto/rea), published as
`rea-agents`, with the official website `rea.tools`. The supplied
`reverseengineeringanything.com` page identifies itself as an independent guide.
It is not the Rootcastle REI project.

REA orchestrates inspection and external analysis engines. Its firmware lane
uses caller-supplied Binwalk 3.1.x and Unblob 26.6.x on Linux x64, with `ps` and
`prlimit`. It does not install those tools or turn encrypted bytes into plaintext.
The documented workflow selects an extracted executable for subsequent native
analysis, rather than treating arbitrary firmware bytes as an executable.
[Firmware guide](https://github.com/morluto/rea/blob/764203cf4a3a3f4ec3c34ebe7049bbd9a04adca9/docs/guides/firmware/firmware-analysis.md)

An isolated trial was performed against the actual downloaded D6 BIN:

| Check | Observed result |
|---|---|
| Package | `rea-agents 6.9.0`, retrieved from the npm registry |
| Runtime | Portable `node-win-x64 24.22.1`; the machine's existing Node 24.19.0 was below the package's supported range |
| `--version` | `6.9.0` |
| `inspect-artifact Neato_4.5.3_189.bin --json` | `unsupported_target`, `file_format_rejected`: unsupported binary format |
| `inspect-firmware-regions ... --json` | `capability_unavailable`: requires Linux and a supplied Binwalk executable |
| Input after both checks | SHA-256 unchanged from the verified firmware digest above |

The package and portable runtime were unpacked beneath the private investigation
directory's `rea-isolated` folder. No global package, Ghidra, Java, WSL, or MCP
agent registration was installed or changed. The two JSON result files are
`artifact-result.json` and `firmware-regions-result.json`; their failures are
recorded evidence, not a claim that extraction succeeded. No target program was
executed, and nothing was sent to the robot.

For the **next** useful native-code investigation, an exported QNX executable is
needed first. REA's native provider can orchestrate Ghidra, including ARM
analysis, but this is not a verified QNX-specific decoder. QNX ELF loader details,
imports, and calling conventions must be checked against the exported program.
The documented Windows Ghidra P0 admission primarily covers native PE and certain
explicit raw/DOS lanes; it does not establish QNX ELF support on Windows.
[Windows boundary](https://github.com/morluto/rea/blob/764203cf4a3a3f4ec3c34ebe7049bbd9a04adca9/docs/providers/windows-ghidra-p0.md),
[raw ARM boundary](https://github.com/morluto/rea/blob/764203cf4a3a3f4ec3c34ebe7049bbd9a04adca9/docs/providers/raw-binary.md)

A minimal appropriate environment would be an isolated Linux x64 analysis host,
a supported Node release, Ghidra 12.1.x with its full JDK 21+, and REA configured
with `GHIDRA_INSTALL_DIR`, `JAVA_HOME`, and `REA_ANALYSIS_PROVIDER=ghidra`.
Binwalk/Unblob are useful for container triage but are not required to inspect an
already exported ELF. Java/Ghidra and WSL were absent on the current Windows
host, and no heavier environment was installed just to disassemble ciphertext.
[Provider installation](https://github.com/morluto/rea/blob/764203cf4a3a3f4ec3c34ebe7049bbd9a04adca9/docs/getting-started/installation.md)

Thus REA is a useful candidate for tracing the native map loader **after
plaintext acquisition**. It did not decode this encrypted update in the actual
trial. Neither an AI interface nor a forced ARM raw import supplies the missing
decryption key, load mapping, or native map schema.

## Follow-up: a real diagnostic artifact, not a native executable yet

The next acquisition trial used the documented Gen3 `uploadLogs` command with
`recentCount: 1`, once, targeting the existing private Vacuula upload sink.
`SvcLogExportManager` was running. The robot accepted the request. The sink
received `BBLog_0000000008.nz.enc.bin` (83,818 bytes), and a private local copy
matched the remote SHA-256:
`ca99f5245e630f803fc8d53c92178dee6816868b6d2a51cebf0cbdc6d5aa8e31`.
Its header starts with ASCII `ZYZY`. Structural inspection identified 27
records: each has a 24-byte header, a payload length at offset 8, and a record
sequence at offset 4 progressing from 1 to 27. The records cover all 83,818
bytes exactly. The initial value 1 is therefore not evidence of a format
version. The field at offset 20 is consistently `0x101`; its meaning is unknown.
This is a genuine acquired diagnostic container, not a demonstrated plaintext
core, ELF, or map. No inference that the old RC4 recipe decodes it is warranted.
The upload-state response advertised 153,408,774 total bytes; that counter alone
does not prove that a file of that size was delivered. A trial using the RC4
key published in the original research did not yield a validated complete
decompression or recognizable executable in the tested framing arrangements.
No working decoder for this 4.5.3 container has been established.

Two bounded serial investigations also established useful limits on 4.5.3:

- `GetDatabase Runtime` and `GetDatabase Robot` returned only their echoes.
  An invalid option produced the actual command's usage error, while an invented
  command produced `Unknown Cmd`: the handler exists, but its accepted options
  did not expose tables over this UART. `All` and `System` were not requested.
- One filtered `GetWifiStatus sloginfo Pattern map` read also returned only its
  echo. No log clearing, Wi-Fi configuration dump, or guessed unlocking key was
  attempted.

The private diagnostic file and redacted serial captures are outside the
repository under `D:/dev/investigate/neato-d6-research`. They must not be
published as ordinary fixtures: robot diagnostics can contain private data.
These probes neither upload a corrected map nor establish a native map import
interface.

The same single diagnostic export subsequently delivered files named
`astro.core`, `dhcpd.core`, `io-pkt-v6-hc.core`, and `Robot.core`, plus compressed
system logs. Their names do not establish plaintext QNX cores: the initially
inspected core files share an opaque prefix and do not have an ELF header.
The historical RC4 key did not produce a valid ELF from the small cores tested.

Unlike those cores, `slogs.bin1.gz` is a valid gzip stream: 335,061 compressed
bytes expand to 2,436,212 bytes. Its historical December 2019 records identify
`/usr/bin/Robot`, `/etc/brain.sh`, `/emmc/Robot.Ini`, transient
`/emmc/maps/FloorMap_0000000001.pgm` and `RunMap_0000000001.pgm`, and the native
`/emmc/persistent_maps/permap_0000000001.bin`. They also show the internal
`ROBOT_GET_MAPID` / `ROSIE_RETURN_MAPID` exchange and Astro's
`BeehiveGetPersistentMaps` handler. These are evidence from this robot's retained
logs, not a current filesystem listing or a proven import operation. In
particular the persistent binary must not be equated with the rendered PGM.

Acquisition then progressed beyond path discovery: the export delivered actual
`permap_0000000001.bin` (4,163,696 bytes), `permap_0000000002.bin`, and
`permap_0000000003.bin` (4,008,036 bytes each). Private copies are retained for
offline format analysis. The native map files are therefore no longer merely
proposed acquisition targets; decoding and a reversible restore remain separate
unproven steps.

Initial offline parsing establishes that these map containers are structured
plaintext, unlike the opaque cores. A 12-byte `TSAM` header contains the exact
file size at offset 8. `TCES` section headers contain a payload length and
section ID; bounded parsing accounts for every byte. Section 0 begins `MAPS`.
Sections 2 and 4 each contain 1,000,000 bytes, and section 5 contains 2,000,000
bytes. Those dimensions suggest grids but do not yet prove width, cell scale,
axes, pixel semantics, or which data the localization engine requires.

The completed acquisition contains 14 native `permap` files. The private
`permap_container.py` parser validates container bounds and section structure,
preserves uninterpreted fields, and reserializes every byte. All 14 files passed
an exact source/reconstructed byte comparison with identical SHA-256 digests
(`cloud-logs/permap-lossless-report.json`). This proves lossless container
handling offline, not that the robot accepts a modified map or that its
localization data can safely be regenerated.

The reusable, local-only reader now lives at `scripts/navigation/permap.py`.
Its strict framing checks cover truncated files, oversized section lengths,
duplicate and unknown IDs, bad magic, and missing leading metadata. Repository
tests pass (62 total), and that implementation also reproduced all 14 private
inputs byte-for-byte. It is deliberately separate from the running coverage
service while payload semantics remain under investigation.

Exploratory offline reshaping of IDs 2 and 4 as 1000-by-1000 uint8 arrays, and
ID 5 as a uint16 little-endian array of the same shape, produces coherent plans
across the acquired maps. Matching shapes are strong empirical evidence for the
layout, but do not establish metric scale or the meaning of a nonzero cell.
ID 5 is sparse in some maps and entirely zero in others. Illustrations use a
shared viewport across layers to avoid implying false relative geometry.

On all 14 files, two signed 16-bit fields at offsets 8/10 of the first `MAPS`
record equal the signed 32-bit values at offsets 16/20 of section 3 divided by
65536. This is evidence of a shared coordinate pair with a representation
compatible with 16.16 fixed point. It does not yet identify an origin, dock
pose, translation, physical units, or coordinate handedness.

Historical 4.2.1-131 system logs also identify `persistentmapdb` schema version 9;
they do not establish the current 4.5.3 database schema. A
complete restoration may therefore involve database-to-file relationships and
running process state, not only replacing a `permap` blob. QNX's `qdbc -B` is
an actual backup operation that writes to a configured destination; it is not
a read-only database discovery command. No database backup/restore or native
map replacement has been performed.
[QNX qdbc reference](https://www.qnx.com/developers/docs/6.5.0SP1.update/com.qnx.doc.qdb_en/qdbc.html)

Before a restoration trial, establish the Map-ID/file/database mapping, acquire
a coherent original snapshot of the relevant database and files, identify the
navigation reload/cache behavior, and verify a rollback to that exact snapshot.
No reliable timestamp was found in the inspected native metadata. File numbers
alone therefore do not prove chronology or identify the currently active map.

Further core inspection did not unlock a native executable. Five acquired core
files are 4096-byte aligned; their early opaque bytes are strongly correlated.
That is compatible with deterministic encryption of similar headers, but does
not identify a cipher or a key. No validated 4.5.3 decoder was found, and no
native code analysis or import claim is based on treating that ciphertext as
an executable.

## Current home: exact links to FloorMap and RunMap

The user confirmed that this D6 has served in several homes. The acquired maps
must therefore not be merged indiscriminately or all calibrated against the
provided current-home floorplan.

Read-only comparison with the active Vacuula FloorMap
`2026-10-17T22:42:28Z` establishes an exact image-level association with native
`permap_0000000014.bin`. Its ID2 grid is cropped to the independently supplied
438-by-328 image extent, then rows are reversed. Coordinates obey
`x_floor = x_native`, `y_floor = 327 - y_native`, with no resampling. Classifying
native bytes as follows reproduces **143,664 of 143,664 pixels exactly**:

| Native ID2 byte | FloorMap class |
| --- | --- |
| 0–59, 100, 200 | free (1) |
| 221–255 | wall (2) |
| remaining values | unknown (0) |

The role of special values 100/200 is not identified from ID2 alone. The
repository's `floor_rows` function reproduces this conversion with an explicit
caller-provided extent; it does not invent native width/height metadata.
Synthetic checks plus real-file validation pass (65 tests total).

ID4 also matches the **RunMap of that map-creation cycle**, not the most recent
cleaning cycle. Applying the same crop/axis convention, ID4 value 0 maps to
background 128 and values 3/4 map to path value 3. All 143,632 non-marker pixels
match exactly. The excluded 32 pixels are the cloud RunMap's 100/200 markers.
The native distinction between 3 and 4 remains unknown. Across all acquired
maps, ID4 additionally contains rare value 16, whose meaning is unresolved.
This is recorded traversal, not evidence of brush/suction operation or complete
room cleaning.

ID5 contains only 0/4 in these files, often all zero, otherwise sparse thin
segments. It has not been identified as a dense room-label image, polygon mask,
or specific kind of constraint. Known room names were not found as ASCII or
UTF-16 strings in ID0/ID1; that does not exclude zone metadata in a database.

This image association identifies the current-home native snapshot without
relying on its sequence number. It does not establish the robot database key,
metric cell size, chronology of all other files, or a restoration procedure.

## Additional native structure observed in metadata

ID0 is 7,936 bytes in these files. Its nonzero prefix consists of up to twelve
68-byte slots, followed by zeros. Across 106 nonzero slots, 98 carry a `MAPS`
tag and eight retain a similar layout with the tag cleared. Each contains five
length/offset pairs at byte pairs (28,32), (36,40), (44,48), (52,56), and
(60,64). Lengths are always 65,536, 40,960, 16,384, 16,384, and 16,384 bytes;
their sum is 155,648. For slot index i, offsets are
`i*155648 + [0,65536,106496,122880,139264]`.

This strongly supports block descriptors, not floating-point metric metadata.
The ID1 section present in the first file is exactly one such 155,648-byte
group. Many descriptor offsets cannot be resolved inside that ID1 payload,
and other files omit ID1 altogether. Their target/storage relationship is
therefore unresolved; these observations must not be treated as a complete
standalone submap format or proof of corruption.

Slot identifiers increase with slot index. A second field references earlier
indices for non-root records, while coordinate pairs and sentinel values differ
between root and non-root records. This is compatible with linked submaps, but
a pose-graph interpretation is not established. A candidate binary-angle
encoding maps two metadata values to almost exactly 2 degrees, while ID3 values
cluster around 0/-90 degrees. This remains an encoding hypothesis, not a
confirmed dock heading or physical-unit specification.

## Metric scale: evidence for 4 cm, not yet a decoded resolution field

All 13 retained robot-reported cleaned-area values are exact decimal multiples
of 0.0016 square metres, the area of a 4 cm square. The reference cycle reports
21.7904 square metres = 13,619 such units. This value originates in the robot's
manifest and is stored unchanged by Vacuula; it is not a server calculation
from the rendered RunMap. Gen3 preserves pixel dimensions (`DOWNSAMPLE=1`).

Together with the supplied physical plan, this supports a strong working
hypothesis of approximately 4 cm per current-map cell. It is not yet a direct
resolution declaration: ID4 has 13,411 nonzero cells, different from the area
counter's 13,619 units. The original FloorMap PNG has no physical-density or
text scale metadata. Vacuula's frontend fallback of 40 mm per cell is an
additional display convention, not a measured Gen3 calibration.
[Display convention](https://github.com/vacuula/vacuula/blob/1d20dd6650d02251c36146003cca168da12971fa/app/src/components/map/drawingFunctions.ts)

No metric resolution was assigned to production coverage data. A physical
calibration should use several independently identified wall lengths in the
current-home map, accounting for unobserved spaces and furniture occlusion.

## Candidate audit and a concrete staging path

A candidate prepared in another worktree filled 5,333 ID2 cells. Independent
reconstruction confirmed byte/container integrity but rejected its evidence
claim for a robot trial: some second votes came only from a dilated neighbour,
some proposed cells had exact opposing votes, and 1,940 changed native bytes
were uncertain values other than the raw neutral 128. Preserving the rendered
FloorMap's known classes is not the same as preserving all observed raw evidence.

The integrated `native_fusion.py` now uses a stricter default for native output:
raw 128 only, at least two exact agreeing votes, zero exact opposing votes, and
no source wall in a 3-by-3 neighbourhood for a free-space proposal. The old
wall-clearing option is disabled. The revised private candidate makes 1,559
changes (1,119 free, 440 wall), preserves every other section, and has SHA-256
`c7b4043e5e950252633d4695e12645cf399d2ce5c96ae90e8c6b0b278e5c1bf4`.
It remains unvalidated: observations may be correlated, ray-like additions
remain, and the relation to native submaps/database state is unresolved.

The bridge upload limit is 65,536 bytes, so a raw 4,008,036-byte map cannot be
sent directly through that route. `stage_payload.py` solves the size constraint
offline with a single-member tar/gzip embedded as base64 in a maintenance
script. The strict candidate produces a final payload of 24,154 bytes. The
script verifies archive hash, extracted length, and file hash, and writes only
under a fresh `/tmp` directory. It neither installs nor reloads a persistent map.
QNX runtime command compatibility and an installed execution hook are separate
